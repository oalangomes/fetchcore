# Configuration reference

**Serving runtime:** `load_runtime_config(path=..., environ=..., overrides=...)` in `fetchcore.application.runtime_config` loads version `1` operator YAML. The top-level sections are `version`, `runtime`, `retrieval`, `backends`, and `embedding`. Precedence is safe defaults < operator YAML < environment < explicit caller overrides. Unknown versions, fields, IDs, invalid URLs, timeouts, and batches fail during bootstrap.

`runtime` selects a built-in backend and may set workspace, repository, revision, knowledge types, and repository paths. `retrieval` maps to `RetrievalConfig` (`dense`, `hybrid`, `reranking`, `ltr`, `targeted`). `backends` holds settings by built-in ID. `embedding.ollama` holds its URL; `retrieval.dense.embedding` owns provider, model, timeout, and request batch. Qdrant `embedding_url` and `embedding_model` remain legacy compatibility inputs.

`FETCHCORE_CONFIG` points to the operator file. `FETCHCORE_BACKEND`, `FETCHCORE_WORKSPACE`, `FETCHCORE_REPOSITORY`, `FETCHCORE_REVISION`, backend endpoint/collection variables, and Ollama overrides are supported; see [the runtime guide](../guides/runtime-configuration.md) for current names and a complete example. Historical `FETCHCORE_MCP_*` values remain compatibility inputs. `FETCHCORE_INDEX_*` configure the separate operational indexing CLI.

Repository-owned `.fetchcore` policy controls corpus admission and indexing behavior, not runtime network endpoints or provider selection. Persisted projection/schema identities are versioned contracts, not arbitrary runtime preferences. See [ADR-0003](../adr/ADR-0003-operator-runtime-configuration.md).

`retrieval.targeted` selects `exact_unique` (default) or `disabled` at the application boundary; see [targeted retrieval](../concepts/targeted-retrieval.md). It does not change the lexical/dense/hybrid mode or persisted projection identity.

Shared Projection v3 controls require a string `projection_version`, string keys in `field_boosts` and `signal_type_boosts`, and finite numeric boost values. Field boosts retain the range `0 < value <= 100`; signal type boosts retain `0 < value <= 10`. `diagnostic_candidate_window`, when set, must be a JSON integer from 1 through 5000. Booleans, numeric strings, floats for the window, and non-finite boosts are invalid.

Solr dense and hybrid retrieval accept `backends.solr.ann_search_breadth` as an optional integer. It sets the Solr KNN `topK` independently of the returned candidate window (`max(max_results, diagnostic_candidate_window)`). If omitted, `topK` equals that window, preserving existing behavior. An explicit breadth must be at least the window and at most the smaller of 5000 or four times the window; invalid values raise a typed configuration error before the dense query. For example, a window of 80 with `ann_search_breadth: 160` requests 160 KNN hits but receives at most 80 candidates for the existing final cutoff and hybrid fusion. This is a Solr adapter setting; it does not change canonical query meaning, embeddings, RRF, persisted fingerprints or other backends. Query metadata and retrieval telemetry expose `ann_top_k_requested`, `dense_candidates_acquired` and `query_vector_sha256` (a digest of the encoded query vector for paired verification); candidate counts are returned candidates, not internal HNSW visits. Larger breadth may cost more latency and does not guarantee exact nearest neighbors. Set it per workload after a controlled quality and cost comparison.
